Once you know what Amazon S3 is, the next question is usually *when not to use it*. AWS has three
core storage services that beginners mix up, because they solve different problems: **Amazon S3**,
**Amazon EBS** and **Amazon EFS**. The quickest way to tell them apart is the *shape* of storage
each one offers.

- **Amazon S3** — *object* storage. You store whole files as objects and fetch them by key over
  the web, from anywhere. No server to attach to.
- **Amazon EBS** (Elastic Block Store) — *block* storage. A virtual disk you attach to a single
  EC2 instance, format with a file system, and use like a local hard drive.
- **Amazon EFS** (Elastic File System) — *file* storage. A managed file system that many EC2
  instances can mount at the same time and share, across Availability Zones.

## Object, block and file — what's the difference?

The three "shapes" aren't AWS jargon; they're the three classic ways to present storage:

- **Object** means each item is a self-contained blob plus metadata, addressed by a key through an
  API. Great for serving and storing lots of independent files; not something you "mount" as a
  disk.
- **Block** means raw fixed-size blocks that an operating system formats and treats as a drive.
  Low latency, written in place — ideal for a database or a boot disk — but attached to one
  instance at a time.
- **File** means a shared file system with directories and POSIX semantics, mounted over the
  network by many clients at once. Ideal when several servers need to read and write the same
  files.

## A side-by-side comparison

| | Amazon S3 | Amazon EBS | Amazon EFS |
|---|---|---|---|
| **Storage type** | Object | Block | File |
| **How you reach it** | API over the web, from anywhere | Attached to one EC2 instance | Mounted by many instances at once |
| **Scope** | Regional, accessed globally | A single Availability Zone | Across Availability Zones |
| **Good for** | Serving files, backups, archives, data lakes | Database disks, boot volumes | Shared file systems for a fleet |
| **Not for** | Low-latency disk I/O for a running OS | Sharing one disk across many instances | Serving objects to the public web |

## How they work together

These aren't rivals you choose once — a real application often uses all three. A web app might run
on EC2 instances with **EBS** boot volumes, share user-uploaded working files across those
instances through **EFS**, and store finished images, backups and logs durably in **S3**. The
skill is matching each kind of data to the storage shape that fits it.

<Callout type="misconception">
"S3 is just AWS's hard drive" is the trap. S3 is *object* storage reached by API — you can't
boot an operating system off it or mount it as a disk the way you would an EBS volume. When you
need a disk for a running instance, that's EBS; when you need a shared file system, that's EFS.
</Callout>

## Key terms

<KeyTerms>
  <Term name="Object storage">Storage where each item is a self-contained object addressed by a key through an API. Amazon S3 is object storage.</Term>
  <Term name="Block storage">Storage presented as raw blocks that an operating system formats and uses as a disk. Amazon EBS is block storage attached to one EC2 instance.</Term>
  <Term name="File storage">A shared file system with directories, mounted over the network by many clients at once. Amazon EFS is file storage.</Term>
  <Term name="Amazon EBS">Amazon Elastic Block Store: block-storage volumes attached to a single EC2 instance in one Availability Zone.</Term>
  <Term name="Amazon EFS">Amazon Elastic File System: a managed file system that many EC2 instances can mount concurrently across Availability Zones.</Term>
</KeyTerms>

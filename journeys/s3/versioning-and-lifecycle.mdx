By default, writing to a key that already exists overwrites it, and deleting a key removes it.
**Versioning** changes that: with it on, S3 keeps every version of an object in the same bucket,
so an overwrite or a delete can be undone. It's the main way to protect objects from mistakes.

## What versioning does

Turn on versioning for a bucket and S3 starts giving each object a **version ID**. From then on:

- A new upload to an existing key doesn't replace the old object — it adds a new *current* version
  and keeps the previous ones beneath it.
- Each version is addressed by **bucket + key + version ID**, so you can read or restore any past
  version, not just the latest.

<Callout type="note">
Once you enable versioning on a bucket you can **suspend** it, but you can't switch it fully back
off. Suspending stops new version IDs being created, while the versions you already have stay
put. So treat enabling versioning as a decision you keep.
</Callout>

## Deletes don't delete: the delete marker

The part that surprises people: with versioning on, a plain delete *doesn't remove any data*.
Instead S3 adds a **delete marker** as the new current version. A `GET` on the key then behaves as
"not found" — but every real version is still there underneath the marker. Remove the delete
marker and the object comes back.

<Callout type="tip">
This is why versioning is the standard defence against the two most common storage accidents:
overwriting a good file with a bad one, and deleting something you still needed. With versioning
on, both are recoverable.
</Callout>

## Lifecycle rules and versions

Keeping every version forever would cost more and more over time. **Lifecycle rules** — the same
mechanism you met in <StepLink service="s3" step="storage-classes">storage classes</StepLink> —
clean up after versioning:

- **Transition** older *noncurrent* versions to cheaper classes after a set time.
- **Expire** noncurrent versions, or clean up expired delete markers, once they're old enough.

So the two features pair naturally: versioning protects against mistakes by keeping history, and
lifecycle rules keep that history from growing without bound.

<Callout type="misconception">
Versioning on its own never saves money — it only ever adds versions. If you turn it on, plan a
lifecycle rule to expire or downgrade old versions, or storage costs will creep up as every
overwrite leaves another version behind.
</Callout>

## Key terms

<KeyTerms>
  <Term name="Versioning">A bucket setting that keeps multiple versions of each object, so overwrites and deletes can be undone. Once enabled it can be suspended but not fully disabled.</Term>
  <Term name="Version ID">The identifier S3 assigns to each version of an object. Bucket + key + version ID addresses one specific version.</Term>
  <Term name="Delete marker">The placeholder S3 adds as the current version when you delete a key in a versioned bucket. It hides the object without removing any version.</Term>
  <Term name="Noncurrent version">Any version of an object that is no longer the current one. Lifecycle rules can transition or expire these.</Term>
</KeyTerms>

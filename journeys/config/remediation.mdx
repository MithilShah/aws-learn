In the <StepLink service="config" step="config-rules">previous step</StepLink> you saw that AWS
Config rules *detect* problems but don't fix them. Remediation is how you close that gap: it
takes a resource that a rule flagged as <CompliancePill status="NON_COMPLIANT" /> and runs an
action to bring it back to <CompliancePill status="COMPLIANT" />.

## How remediation works

AWS Config applies remediation using **AWS Systems Manager (SSM) Automation documents**. An
Automation document defines the actions to perform on a noncompliant resource. AWS Config provides
a set of *managed* Automation documents with ready-made remediation actions, and you can also
create and associate your own *custom* documents. You associate a document with a rule from the
AWS Management Console or through the API.

<Callout type="note">
Remediation is a separate, deliberate step after detection. A rule finding a resource
noncompliant does not change the resource — associating a remediation action, and then running
it, is what changes anything.
</Callout>

## Manual or automatic

You choose how remediation is triggered. The flow is the same either way; what differs is who
pulls the trigger.

- **Manual remediation** gives you a reviewed, deliberate fix: a resource is flagged, and a
  person decides to run the remediation. Good when a change needs a human to confirm it's safe.
- **Automatic remediation** closes the loop without anyone watching: once associated, the action
  runs as soon as the resource is noncompliant. Good for well-understood fixes you trust to run
  unattended.

<Callout type="tip">
If an automatic remediation doesn't succeed, AWS Config can retry. Start a new remediation with
manual triggering while you build confidence in an action, then switch it to automatic once you
trust it.
</Callout>

## The example document

The flow above uses a real managed Automation document, **`AWS-DisableS3BucketPublicReadWrite`**.
It uses Amazon S3 Block Public Access to disable public read and write access on a bucket. It
takes the bucket name (`S3BucketName`, required) and an optional IAM role
(`AutomationAssumeRole`) that lets Systems Manager act on your behalf. Paired with the
`s3-bucket-public-read-prohibited` rule, it turns "this bucket is public" into "this bucket is
locked down" with a single, repeatable action.

## Managed and custom documents

As with rules, you don't have to build everything yourself:

- **Managed Automation documents** — AWS provides a prepopulated list of remediation actions in
  the console, like `AWS-DisableS3BucketPublicReadWrite`.
- **Custom Automation documents** — when no managed document does what you need, you write your
  own SSM document and associate it with the rule.

Remediation handles one resource at a time. The next step,
<StepLink service="config" step="conformance-packs-and-aggregators">conformance packs and
aggregators</StepLink>, scales rules and their remediations up to many accounts and Regions.

## Key terms

<KeyTerms>
  <Term name="Remediation">An action AWS Config runs to bring a noncompliant resource back into compliance, defined by an SSM Automation document.</Term>
  <Term name="SSM Automation document">An AWS Systems Manager document that defines the actions to perform on a noncompliant resource. AWS Config provides managed documents, and you can create custom ones.</Term>
  <Term name="Manual remediation">Remediation that a person triggers after a resource is flagged noncompliant.</Term>
  <Term name="Automatic remediation">Remediation that AWS Config runs on its own as soon as a resource is noncompliant, once the action is associated with the rule.</Term>
</KeyTerms>

When you turn on AWS Config, it first discovers the supported resources in your account and
creates a configuration item for each one. It then keeps recording new configuration items as
those configurations change. This step follows a single change through that pipeline, from the
moment it happens to where the record ends up.

## Resource discovery and tracking

The moment you turn on AWS Config, it discovers the supported resources that already exist in
your account and generates a configuration item for each one. By default it records every
supported resource type in the Region, but you can narrow that to just the resource types you
care about.

After that, AWS Config keeps track of changes by calling each resource's `Describe` or `List`
API. It uses those same calls to capture the *related* resources too, so a single change can
produce several configuration items.

<Callout type="tip">
AWS Config also catches changes that didn't come through an API. It periodically re-examines your
resource configurations and records a configuration item for anything that has changed since it
last looked.
</Callout>

## A change moving through the pipeline

Here is the AWS documentation's own example. You remove an egress rule from a security group.
AWS Config calls `Describe` on that security group, then calls `Describe` on every instance
associated with it. It records the updated security group and each instance as configuration
items, and delivers them in the configuration stream to your Amazon S3 bucket.

## What's inside a configuration item

A configuration item is a point-in-time view of the attributes of a supported resource. The AWS
documentation breaks it into five components.

- **Metadata** — version ID, when the item was captured, its status, and a state ID that orders a
  resource's items.
- **Attributes** — resource ID, tags, resource type, ARN, Availability Zone (if any), and creation
  time.
- **Relationships** — how this resource relates to others, such as *EBS volume vol-1234567 is
  attached to EC2 instance i-a1b2c3d4*.
- **Current configuration** — what the resource's `Describe` or `List` API returns, for example the
  details `DescribeVolumes` returns about an EBS volume.
- **Related events** — a field that has been empty since version 1.3.

<Callout type="note">
The `relatedEvents` field is empty as of version 1.3. To find the API events behind a change, use
the `LookupEvents` API in AWS CloudTrail — which is exactly the division of labour the
<StepLink service="config" step="config-vs-cloudtrail-vs-cloudwatch">last step</StepLink>
explores.
</Callout>

## The configuration recorder and how often it records

The configuration recorder is the part that stores configuration changes as configuration items.
It comes in two kinds: a *customer managed* recorder, where you choose the resource types in
scope, and a *service-linked* recorder, where a specific AWS service sets the scope.

You also choose how often AWS Config records. The two frequencies behave quite differently:

<Tabs label="Recording frequency">
  <TabPanel label="Continuous recording">

  AWS Config records a configuration change **whenever a change occurs**. This gives you real-time
  detection of unauthorized or unexpected changes and lets you analyse changes as they happen.

  *AWS Firewall Manager depends on continuous recording, so AWS recommends continuous if you use
  it.*

  </TabPanel>
  <TabPanel label="Daily recording">

  AWS Config delivers one configuration item representing the **most recent state** of a resource
  over the last 24 hours — and **only if it differs** from the previous one. This means a quieter
  flow of notifications and lower cost when you don't need change-by-change detail.

  </TabPanel>
</Tabs>

## Where the data goes

AWS Config delivers through two channels:

- **An Amazon S3 bucket.** For each recorded resource type, AWS Config sends a *configuration
  history file every six hours* describing the resources of that type that changed in the period
  (if none changed, it sends nothing). On request — the `deliver-config-snapshot` CLI command or
  the `DeliverConfigSnapshot` API — it also sends a *configuration snapshot* covering every
  recorded resource. Both are JSON.
- **An Amazon SNS topic.** AWS Config sends notifications here. The one delivered within minutes of
  every change is the `ConfigurationItemChangeNotification`, and the running list of these is
  called the **configuration stream**.

## Asking questions about your resources

Once AWS Config is recording, you don't have to read raw JSON to answer a question. *Advanced
queries* let you query the current configuration state of your resources with SQL-like
statements, either from a library of sample queries or your own. For example, you could list
every EC2 instance of a given type, or every S3 bucket, across the resources AWS Config records.

## Key terms

<KeyTerms>
  <Term name="Configuration item">A point-in-time view of the attributes of a supported AWS resource, made up of metadata, attributes, relationships, current configuration and related events.</Term>
  <Term name="Configuration recorder">The part of AWS Config that stores configuration changes to the resource types in scope as configuration items.</Term>
  <Term name="Configuration history">A collection of a resource's configuration items over a period of time, delivered as a history file to Amazon S3 every six hours per resource type.</Term>
  <Term name="Configuration snapshot">A point-in-time collection of configuration items for every recorded resource, delivered to Amazon S3 on request.</Term>
  <Term name="Configuration stream">The automatically updated list of configuration items, delivered as change notifications through Amazon SNS.</Term>
</KeyTerms>

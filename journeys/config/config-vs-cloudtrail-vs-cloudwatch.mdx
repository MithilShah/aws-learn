AWS Config, AWS CloudTrail and Amazon CloudWatch all help you keep an eye on your AWS account, so
they're easy to mix up. The quickest way to tell them apart is by the question each one answers.

- **AWS Config** — *What did my resource look like?* It keeps a configuration history, so you can
  see how a resource was set up at any point in time.
- **AWS CloudTrail** — *Who made the API call?* It records user API activity, including the
  identity behind each action.
- **Amazon CloudWatch** — *How is my resource performing?* It collects metrics and logs and raises
  alarms in near real time.

## A side-by-side comparison

| | AWS Config | AWS CloudTrail | Amazon CloudWatch |
|---|---|---|---|
| **Answers** | What did my resource look like? | Who made the API call? | How is my resource performing? |
| **Records** | Configuration items over time | User API activity | Metrics, logs and events |
| **Good for** | Inventory, change history, compliance | Auditing and security forensics | Monitoring, alarms and dashboards |
| **Typical output** | Configuration history and compliance | An audit trail of API calls | Graphs, dashboards and alarms |

## How Config and CloudTrail work together

These services aren't rivals — they're often used side by side. AWS Config shows you *what*
changed; CloudTrail shows you *who* changed it.

The AWS Config FAQ gives a concrete example. Suppose you use AWS Config to detect that the
security group **"Production-DB"** was incorrectly configured in the past. AWS Config shows you
the misconfiguration in the resource's history — but not who caused it. Using the integrated
CloudTrail information, you can then pinpoint which user misconfigured the "Production-DB"
security group.

<Callout type="misconception">
A noncompliant finding in AWS Config tells you *what* is wrong, not *who* did it. For the identity
behind a change, you reach for CloudTrail — the two together give you the full picture. (In fact,
all AWS Config API activity is itself logged by CloudTrail.)
</Callout>
